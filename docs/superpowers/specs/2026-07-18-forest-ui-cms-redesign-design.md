# Forest 공개 UI·관리자 CMS 핵심 구조 개편 설계

- 작성일: 2026-07-18
- 상태: 사용자 승인 완료, 구현 전 설계
- 대상 저장소: `cms-react-project` 중심, 격리형 통합 E2E 기반은 `forest` 연계
- 배포 정책: 초안 검토 전 푸시·운영 배포 금지

## 1. 배경

Forest는 전북생명의숲의 공개 홈페이지와 운영자 CMS를 함께 제공한다. PRD의 주 사용층은 50~60대이며, 현재 화면은 18px 본문, 48px 터치 영역, 카드형 프로그램 목록 등 기본적인 고연령 사용자 배려를 이미 갖추고 있다.

벤치마크인 울산생명의숲 사이트(`https://usforest.or.kr/index.php`)는 다음 강점이 있다.

- 지역 숲과 단체 정체성이 첫 화면에서 분명하다.
- 공지와 프로그램 정보를 빠르게 찾을 수 있다.
- 프로그램 목록·상세에 대상, 행사일, 정원, 접수 상태 등 의사결정 정보가 모여 있다.

반면 작은 글씨의 표, 모바일에서 겹치는 요소, 과도하게 긴 신청 양식 등은 Forest의 50~60대 사용자를 위해 답습하지 않는다. Forest의 큰 글씨·카드형 UI를 유지하면서 벤치마크의 정보 우선순위와 지역성을 결합하는 `핵심 구조 개편`을 선택한다.

## 2. 목표와 비목표

### 목표

1. 공개 메인에서 전북 지역성과 단체 목적을 명확히 전달한다.
2. 프로그램, 공지, 최근 활동 등 핵심 정보를 적은 단계로 찾게 한다.
3. 공개 UI와 관리자 CMS가 하나의 접근 가능한 디자인 체계를 사용하게 한다.
4. 관리자에게 프로그램과 게시글의 조회·수정·삭제 상태를 명확히 보여준다.
5. 모바일 390px와 데스크톱에서 동일한 핵심 업무를 수행할 수 있게 한다.
6. UI E2E와 격리된 실제 API E2E를 완료 게이트로 만든다.
7. 클릭 가능한 로컬 초안과 화면 캡처를 먼저 검토받고, 승인 전에는 푸시·배포하지 않는다.

### 비목표

- 울산생명의숲의 화면이나 코드를 그대로 복제하지 않는다.
- 이번 초안에서 기존 API URL이나 데이터 계약을 임의로 깨지 않는다.
- 카테고리 수정, INFORMATION 갤러리 전체 편집, ESG·자료실 관리자 편집처럼 현재 API·UI가 완성되지 않은 기능을 동작하는 것처럼 표시하지 않는다.
- 운영 계정, 운영 DB, 운영 파일 저장소를 테스트 데이터 생성에 사용하지 않는다.
- E2E 통과를 근거로 “모든 버그가 없다”거나 특정 WCAG 등급을 완전히 준수한다고 과장하지 않는다.

## 3. 사용자와 접근성 원칙

주 사용층 50~60대를 기준으로 다음을 기본값으로 둔다.

- 본문 18px 이상, 줄간격 1.7 이상, 리치 본문 최대 72ch
- 주요 조작 영역 최소 48×48px
- 버튼은 색뿐 아니라 텍스트와 모양으로 역할 구분
- 흰 배경의 일반 크기 텍스트·버튼에는 현재의 밝은 `green-600` 대신 더 진한 의미 기반 녹색 사용
- 키보드 포커스 표시, 모달 포커스 순환, Escape 종료, 종료 후 원래 위치 복귀
- 자동 재생은 사용하지 않거나 일시정지 제어 제공
- 로딩·오류·빈 상태를 구분하고 오류에는 `다시 시도` 제공
- 모바일에서 가로로 밀리는 관리 표는 카드로 전환
- 한 화면의 주 행동은 하나로 두고, 삭제 등 위험 행동은 시각적으로 분리

## 4. 공개 정보 구조

### 4.1 헤더와 내비게이션

상위 탐색은 다섯 영역을 중심으로 정리한다.

1. 단체소개
2. 참여 프로그램
3. 소식
4. 자료실
5. 후원하기

현재 동적 게시판과 ESG 경로는 제거하지 않고 관련 상위 메뉴의 하위 항목으로 배치한다. 정확한 하위 메뉴 매핑은 기존 카테고리 데이터를 보존한 채 클릭 가능한 초안에서 검증한다. 데스크톱은 한 줄에 무제한 동적 게시판을 나열하지 않으며, 모바일은 기존의 계층형 드로어와 포커스 트랩을 유지한다.

추가 원칙은 다음과 같다.

- 본문 바로가기 링크 제공
- URL을 기준으로 현재 메뉴와 부모 메뉴를 함께 표시
- `프로그램 참여` 또는 `후원하기` 중 현재 페이지의 핵심 행동만 강조
- 로그인·관리자 진입은 핵심 공개 탐색과 시각적으로 분리

### 4.2 메인 화면 순서

#### A. 대표 배너

- 전북 지역의 실제 숲·활동 사진을 우선 사용한다.
- 첫 화면에는 하나의 짧고 구체적인 메시지와 `프로그램 참여` 주 버튼을 둔다.
- 필요할 때만 `단체 소개`를 보조 링크로 제공한다.
- 사진 위 텍스트 대비를 검증하고, 화살표가 제목을 가리지 않게 한다.
- 다중 배너가 필요하면 자동 전환을 기본 비활성화하거나 일시정지 버튼을 제공한다.

실제 사진의 저작권과 초상권을 확인하기 전까지 클릭 가능한 초안에는 기존 승인 자산 또는 명확한 플레이스홀더를 사용한다.

#### B. 진행 중인 프로그램

메인 배너 바로 아래에 배치한다. 프로그램 카드에는 가능한 범위에서 다음을 제공한다.

- 접수 상태
- 프로그램명
- 참여 대상
- 행사 일시
- 장소
- 정원 또는 잔여 인원
- 명확한 `자세히 보기` 버튼

현재 API에 없는 값은 추측하지 않고 숨기거나 `상세에서 확인`으로 표시한다. 모바일은 한 열, 넓은 화면은 최대 세 열로 구성한다.

#### C. 중요 공지

- 최신 또는 고정 공지 3~5개와 날짜를 보여준다.
- 긴 제목은 모바일에서 두 줄까지 허용한다.
- 목록 전체 보기 링크를 명확히 제공한다.

#### D. 최근 활동과 소식

- 실제 활동 사진 중심 카드 3개를 기본으로 한다.
- 카테고리, 제목, 게시일을 함께 표시한다.
- 이미지가 없어도 정보 계층이 무너지지 않는 대체 카드가 있어야 한다.

#### E. 후원·참여 안내

- 후원과 자원봉사를 분리해 설명한다.
- 각 카드에는 하나의 행동 버튼만 제공한다.

### 4.3 프로그램 목록과 상세

- `/programs`에서 소개 카드만 보여주고 다시 목록으로 이동하게 하는 단계를 줄인다.
- 기존 카드형 목록을 유지하면서 현재 계약이 제공하는 행사일, 정원, 접수 상태를 먼저 보강한다.
- 상세 상단에 신청 판단에 필요한 정보를 요약한다.
- 원문 URL은 그대로 노출하지 않고 `관련 안내 보기`와 같은 설명 링크로 바꾼다.
- `구글폼 신청하기`와 `홈페이지에서 신청하기`를 같은 무게로 동시에 노출하지 않는다. 프로그램별 실제 신청 방법 하나를 주 행동으로 정하고, 대체 방법이 꼭 필요할 때만 보조 링크로 제공한다.

현재 공개 프로그램 상세 계약에는 참여 대상, 장소, 현재 신청 인원이 없다. 첫 초안은 이 값을 만들거나 본문에서 임의 추출하지 않는다. 해당 정보와 잔여 인원 표시는 별도 백엔드 계약 확장 후보로 표시하고, 추가 승인을 받기 전에는 행사일·최대 정원·접수 상태만 사용한다.

## 5. 시각 체계

기존 `src/assets/logo.png`는 첫 초안에서 형태·색을 변경하지 않는다. 녹색 계열은 현재 팔레트 안에서 의미 기반 토큰으로 정리한다.

- `color-brand-primary`: `#166534`(현재 green-800), 흰색 대비 약 7.13:1
- `color-brand-strong`: `#14532d`(현재 green-900), 흰색 대비 약 9.11:1
- `color-brand-surface`: `#f8faf5`를 후보로 사용하는 밝은 중립 배경
- `color-accent`: `#b45309`를 후보로 사용하며, 흰색 텍스트를 쓸 때 대비 약 5.02:1
- `color-danger`, `color-warning`, `color-success`: 텍스트와 아이콘을 함께 사용하는 상태색
- `surface-card`, `surface-raised`, `border-subtle`, `focus-ring`: 공개·관리자 공용 표면 토큰

정확한 표면색과 포인트색은 화면 캡처 승인으로 확정하되, 로고는 별도 승인 없이 수정하지 않는다. 공통 컴포넌트는 색·크기·상태를 자체적으로 보장한다. 페이지에서 임의의 작은 `text-xs`, 낮은 대비 녹색, 48px 미만 아이콘 버튼을 새로 만들지 않는다.

## 6. 관리자 CMS

### 6.1 관리자 셸과 홈

데스크톱은 지속적인 측면 탐색, 모바일은 제목과 현재 영역을 명확히 보여주는 드로어를 사용한다. 관리자 홈에는 실제 API로 확인 가능한 업무 바로가기만 둔다.

- 프로그램 관리
- 신청자 관리
- 게시글·소식 관리
- 공지 관리
- 후원 요청

확인할 수 없는 통계나 성과 수치를 만들지 않는다.

### 6.2 프로그램 관리

- 접수 중·예정·종료 상태 필터
- 제목 검색과 기간 필터
- 모바일 카드, 데스크톱 표
- 수정·신청자 확인을 주 작업으로 배치
- 삭제는 별도 위험 영역과 확인 절차 제공
- 중복 클릭 방지, 처리 중 표시, 성공·실패 피드백
- 목록 복귀 시 검색·필터·페이지 위치 보존

### 6.3 통합 게시글 관리

소식, 공지, 동적 게시판을 같은 관리 패턴으로 다루되 API별 계약은 유지한다.

- 유형 또는 게시판 전환
- 제목 검색
- 제목, 게시판, 작성일, 공개 상태, 수정 작업 표시
- 모바일 카드, 데스크톱 표
- 수정 후 원래 검색 조건과 목록 위치 복귀
- 기존 이미지·첨부와 새 업로드 항목 구분
- API가 완성되지 않은 편집 기능은 읽기 전용 또는 `준비 중`으로 명시

### 6.4 작성·수정 화면

- 기본정보, 본문, 이미지·첨부 영역을 시각적으로 구분
- 저장과 취소를 쉽게 찾을 수 있는 하단 작업 영역
- 미저장 이탈 경고
- 검증 오류를 필드 가까이에 표시하고 첫 오류로 포커스 이동
- 저장 중 중복 요청 방지
- 실패 시 입력 내용을 유지하고 사람이 이해할 수 있는 메시지 제공

### 6.5 관리자 접근성

모든 모달은 `dialog` 의미, 제목 연결, 닫기 레이블, 포커스 순환, Escape 종료, 원래 포커스 복귀를 제공한다. 클릭 가능한 행만 두지 않고 실제 버튼이나 링크를 제공한다.

## 7. 컴포넌트 구조

기존 대형 페이지를 한 번에 재작성하지 않고 다음 경계로 분리한다.

### 공통 UI

- `Button`, `IconButton`
- `FormField`
- `StatusBadge`
- `AccessibleDialog`
- `AsyncState`
- `ResponsiveDataView`

### 공개 화면

- `DesktopNav`, `MobileNav`, `SiteFooter`, `LoginDialog`
- `HomeHero`
- `ProgramCard`
- `NoticeList`
- `ActivityCard`
- `ParticipationCallout`

### 관리자

- `AdminShell`, `AdminNav`
- `AdminHomePanel`
- `ProgramPanel`
- `ContentPanel`
- `ProgramEditor`

현재 `Layout`, `UserHome`, `AdminDashboard`의 데이터 계약과 상태를 먼저 테스트로 고정한 뒤, 위 경계를 따라 점진적으로 추출한다.

## 8. 데이터 흐름과 오류 처리

### 8.1 데이터 원칙

- 기존 React Query와 서비스 계층을 유지하고 화면에서 직접 새 API 계약을 만들지 않는다.
- 목록의 검색·필터 상태는 URL 쿼리 또는 명시적 라우트 상태로 보존한다.
- 수정 성공 후 관련 쿼리만 무효화하고 원래 목록 상태로 복귀한다.
- 삭제는 서버 성공 응답 뒤 목록에서 제거한다.
- 프로그램과 게시글의 API 형태가 다르면 UI만 통일하고 요청 모델을 억지로 합치지 않는다.

### 8.2 상태 처리

모든 주요 화면은 다음 상태를 명시한다.

1. 초기 로딩
2. 데이터 있음
3. 빈 상태
4. 인증 필요 또는 권한 부족
5. 네트워크·서버 오류와 다시 시도
6. 저장·삭제 처리 중
7. 성공 피드백

404나 잘못된 딥링크를 홈으로 조용히 보내지 않고 원인을 설명하는 화면과 안전한 이동 경로를 제공한다.

## 9. 클릭 가능한 초안

첫 검토본은 별도 작업 공간과 로컬 실행 환경에서 제작한다.

초안은 버전 관리되는 고정 mock fixture를 사용한다. 실행 명령 하나로 동일 데이터를 재현할 수 있어야 하며, API mock 상태에서는 화면에 `로컬 초안` 표시를 제공한다. 아직 연결하지 않은 버튼은 성공한 것처럼 보이게 하지 않고 비활성화 또는 `초안에서는 지원하지 않음`으로 표시한다.

| 공개 메인 | `/`와 공통 헤더·모바일 드로어 | 대표 배너, 프로그램·공지·활동·후원 섹션의 순서와 반응형, 메뉴 키보드 조작, 카드 링크가 기존 목적지로 이동하는지 |
| 공개 연결 목적지 회귀 | 기존 `/programs/participate`, `/news/notice`, `/news/activities` | 링크 목적지가 오류 없이 렌더링되는지만 확인하며 첫 초안에서 목록·상세 화면을 재설계한 것으로 표시하지 않음 |
| 관리자 홈 | 계획된 `/admin?section=home` | 권한 가드, 업무 바로가기, 모바일·데스크톱 탐색 |
| 프로그램 관리 | `/admin?section=programs`, `/programs/edit/:id` | 목록·검색·필터·수정·복귀 흐름과 오류 상태 |
| 통합 게시글 관리 | 계획된 `/admin?section=content`, 기존 `/category/:categoryId/edit/:postId`, `/news/notice/edit/:noticeId` | 유형 전환, 검색, 수정·복귀 흐름과 오류 상태 |
| 기존 CRUD 회귀 | `/programs/create`, `/programs/detail/:id`, 기존 게시글·공지 작성·상세·삭제 경로 | 시각 재설계 대상이 아닌 등록·조회·삭제 동작을 회귀 테스트로만 검증 |

프로그램 목록·상세의 정보 보강은 4.3의 후속 공개 화면 범위다. 공개 메인 1차 승인은 해당 화면의 재설계 완료에 묶지 않는다.

검토물:

- 실제 클릭 가능한 로컬 화면
- 데스크톱·모바일 화면 캡처
- 변경 전후 정보 구조 요약
- 아직 연결되지 않은 기능과 테스트 제약 목록

사용자 승인 전에는 원격 푸시, PR 병합, Vercel 또는 백엔드 운영 배포를 하지 않는다.

검토 순서는 다음처럼 분리한다.

1. 공개 메인·브랜드 클릭 초안과 UI E2E 결과 검토
2. 승인된 공개 디자인을 적용한 관리자 CMS 클릭 초안과 UI E2E 결과 검토
3. 격리된 실제 API CRUD E2E와 릴리스 준비 상태 검토

따라서 공개 메인 초안은 관리자 전체와 통합 E2E 기반이 완성될 때까지 숨겨두지 않는다. 각 단계의 미완료 범위를 함께 표시한다.

## 10. E2E 전략

### 10.1 현재 제약

현재 프런트에는 Playwright·Cypress 설정과 테스트가 없다. 개발 API는 `http://localhost:8080/api/v1`, 운영 API는 `https://forest.platformholder.site/api/v1`로 코드에 고정되어 있고 OAuth는 실제 플랫폼 도메인을 사용한다. 백엔드는 MySQL, MongoDB, Redis, Kafka, auth, storage 연동을 요구하지만 격리된 test profile과 Testcontainers가 없다.

따라서 브라우저 API mock 테스트만으로 실제 CRUD 통합을 통과했다고 주장하지 않는다. 반대로 운영 또는 공유 dev 환경에서 데이터를 만들고 지우는 방식도 사용하지 않는다.

### 10.2 1단계: 결정적 UI E2E

프런트에 Playwright를 도입하고 브라우저 네트워크 라우팅으로 API 응답을 격리한다.

아래 목록은 단계가 진행되면서 누적되는 UI 회귀 범위이며, 각 초안의 통과 범위는 9절의 매핑과 10.5절의 단계별 게이트를 따른다.

- Chromium 기준 데스크톱, 768px 태블릿, 390px 모바일 프로젝트
- 공개 홈, 내비게이션, 프로그램·공지·게시글 목록과 상세
- USER·ADMIN·미인증 권한 상태
- 프로그램 등록→조회→수정→삭제 UI
- 게시글·공지 등록→조회→수정→삭제 UI
- 신청 폼 검증, 로그인 후 복귀, 성공·중복·마감·오류
- 로딩·빈 상태·404·500·재시도
- 삭제 확인, 중복 클릭 방지, 미저장 이탈 경고
- 키보드 탐색, 포커스, 주요 접근성 자동 검사
- 콘솔 오류와 예상하지 않은 요청 실패 감지

이 단계는 UI 상태와 프런트가 기대하는 요청 형태를 검증한다. mock fixture와 UI가 함께 잘못될 수 있으므로 실제 API 계약 검증으로 부르지 않으며, 백엔드 DTO 또는 OpenAPI 기반 schema/contract test와 실제 저장소 통합 E2E를 별도로 보고한다.

### 10.3 2단계: 격리된 실제 API E2E

다음 기반을 만든 뒤에만 실제 CRUD E2E를 실행한다.

- `VITE_API_BASE_URL` 등 테스트 전용 URL 주입
- `application-test.yml`
- Testcontainers 의존성과 반복 가능한 Flyway test seed
- 임시 MySQL·MongoDB·Redis 컨테이너
- `eureka.client.enabled=false`
- Kafka, 스케줄러, 비동기 listener를 test profile에서 조건부 비활성화하거나 test double로 교체
- test profile에서만 활성화되는 auth·storage test double
- 외부 gRPC discovery·auth·storage bean이 실제 네트워크에 연결되지 않는지 시작 시 검증
- 무작위 localhost 포트와 테스트별 데이터 네임스페이스
- 테스트 종료 시 DB와 컨테이너 폐기
- 프런트와 백엔드 양쪽에서 test profile 활성화와 ephemeral DB 식별자를 함께 확인
- URL을 파싱해 `localhost`, `127.0.0.1`, `::1`과 현재 테스트가 만든 컨테이너 네트워크만 허용하는 allowlist
- allowlist, test profile, ephemeral DB 확인 중 하나라도 실패하면 쓰기 테스트를 시작하지 않는 fail-closed 가드

쓰기 허용 프로토콜은 다음 순서를 따른다.

1. 단일 Testcontainers runner가 MySQL·MongoDB·Redis를 만들고 매 실행마다 임의의 `runId`, 실제 container ID, mapped host·port를 보유한다.
2. runner가 그 실행 manifest를 백엔드 test process에 직접 주입한다.
3. test source set의 백엔드 startup validator가 활성 profile, 실제로 해석된 MySQL·MongoDB·Redis 연결 주소, manifest의 container ID·mapped host·port를 대조한다.
4. 모두 일치할 때만 test source set에 존재하는 readiness endpoint가 해당 `runId`를 반환한다. 불일치하면 백엔드 시작 자체를 실패시킨다.
5. Playwright는 API base URL이 loopback인지 확인하고, runner가 전달한 `runId`와 readiness 응답이 일치한 뒤에만 쓰기 시나리오를 실행한다.
6. 프런트는 DB 식별자를 직접 신뢰하거나 임의 환경변수 하나만으로 쓰기를 허용하지 않는다.

프로덕션 코드에서 사용할 수 있는 우회 인증 경로는 만들지 않는다. 실 OAuth 검증은 별도 staging 앱·DB·계정이 준비된 경우의 최소 smoke test로 제한하며, 이번 로컬 초안의 완료 조건에는 포함하지 않는다.

### 10.4 누적 최종 E2E 시나리오

아래는 세 단계가 끝난 뒤의 누적 회귀 범위다. 공개 메인 1차 초안 게이트가 모든 공개 상세 화면의 재설계를 요구한다는 의미가 아니다.

#### 공개

1. 홈 로드와 핵심 섹션 순서
2. 모바일 메뉴 열기·계층 탐색·닫기·포커스 복귀
3. 프로그램 목록→상세→신청 진입
4. 공지·소식 목록→상세
5. 잘못된 URL과 서버 오류 복구

#### 관리자

1. 권한 가드와 관리자 홈 진입
2. 프로그램 등록→상세 확인→수정→목록 상태 유지→삭제
3. 게시글 등록→상세 확인→수정→목록 상태 유지→삭제
4. 공지 등록→수정→삭제
5. 신청자 목록과 상세 열기
6. 실패 응답, 재시도, 중복 제출 방지
7. 모든 대화상자의 키보드 조작

### 10.5 단계별 완료 게이트

#### 공개 메인 초안 검토 게이트

- 프런트 lint와 production build 통과
- `/`와 공통 헤더의 데스크톱·768px 태블릿·390px 모바일 UI E2E 통과
- 메인 카드가 기존 프로그램·공지·활동 목적지로 오류 없이 이동
- 200% 확대 reflow와 `prefers-reduced-motion` 검증
- 메인에서 프로그램 찾기, 공지 찾기, 프로그램 참여 경로 진입 대표 과업의 키보드·수동 검토
- 예상하지 않은 브라우저 콘솔 오류와 실패 요청 없음
- 주요 화면 캡처의 수동 시각 검토
- mock 데이터와 미연결 기능을 화면과 결과에 명시

#### 관리자 CMS 초안 검토 게이트

- `/admin?section=home`, `/admin?section=programs`, `/admin?section=content`와 프로그램·게시글·공지 수정 경로의 UI E2E 통과
- 기존 등록·상세·삭제 경로는 시각 개편과 구분된 mock 회귀 E2E 통과
- 데스크톱·768px 태블릿·390px 모바일에서 동일 업무 완료
- 200% 확대 reflow, 키보드 탐색, 모달 포커스 검증
- 검색·필터·목록 위치 복귀와 오류 복구 검증
- 예상하지 않은 브라우저 콘솔 오류와 실패 요청 없음

#### 통합·릴리스 준비 게이트

- 기존 백엔드 단위 테스트 통과
- 백엔드 DTO/OpenAPI와 프런트 fixture의 schema/contract 검증 통과
- 격리된 실제 API E2E의 프로그램·게시글·공지 CRUD 통과
- fail-closed 운영 차단 가드 자체 테스트 통과
- 테스트 데이터와 컨테이너 자동 폐기 확인
- 알려진 제한과 미검증 범위를 결과에 명시

초안은 앞 단계 게이트를 통과할 때마다 사용자에게 공개한다. 실제 반영 논의는 세 게이트를 모두 통과하고 사용자가 별도로 승인한 뒤 시작한다.

## 11. 위험과 완화

| 위험 | 완화 |
| --- | --- |
| 실제 지역 사진의 권리 불명확 | 승인 자산 또는 플레이스홀더로 초안 제작 후 권리 확인 |
| 기존 동적 게시판이 새 메뉴에서 누락 | 모든 기존 route와 category를 매핑표로 검증 |
| 대형 컴포넌트 분리 중 회귀 | 현재 동작을 E2E로 고정하고 작은 경계부터 추출 |
| 프로그램·게시글 API 차이를 과도하게 통합 | UI 패턴만 공유하고 서비스·요청 모델은 분리 |

## 12. 승인 및 다음 단계

사용자는 다음을 승인했다.

- 우선순위: 공개 메인·브랜드 개편 후 관리자 CMS 개선
- 접근법: 부분 수정이나 전면 재구축이 아닌 핵심 구조 개편
- 브랜드: 기존 로고·녹색 유지, 전북 지역 사진 중심 현대화
- 검토 방식: 운영 반영 전 클릭 가능한 로컬 초안과 모바일·데스크톱 캡처 제공
- 테스트: 운영 데이터를 사용하지 않는 UI E2E와 격리된 실제 CRUD E2E 포함

다음 단계는 이 설계를 자체 검토하고 사용자에게 명세 검토를 요청한 뒤, 별도의 구현 계획을 작성하는 것이다.
