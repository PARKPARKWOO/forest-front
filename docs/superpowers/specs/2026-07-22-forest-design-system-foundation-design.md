# Forest 프로젝트 내 디자인 시스템 기반 설계

- 작성일: 2026-07-22
- 상태: 기반·배너/조직도 대표 파일럿 구현 및 검증 완료, 조직도 나머지 및 전체 레거시 전환 대기
- 대상 저장소: `cms-react-project`
- 관련 설계: `2026-07-18-forest-ui-cms-redesign-design.md`
- 배포 정책: 이 문서 승인과 후속 구현 검증 전에는 원격 푸시·운영 배포를 진행하지 않는다.

## 1. 결정 요약

Forest 디자인 시스템은 별도 저장소나 독립 배포 패키지로 만들지 않는다. 공개 홈페이지와 관리자 CMS가 함께 있는 현재 프런트엔드 저장소 안에서 하나의 디자인 기준과 공용 컴포넌트를 관리한다.

다른 서비스와는 UI 코드를 복사하거나 공용 패키지로 묶지 않는다. 서비스마다 사용자, 브랜드, 플랫폼이 다르기 때문이다. 서비스 간에는 최소 글자 크기, 터치 영역, 키보드 접근, 명도 대비, 모션 절제 같은 접근성·품질 원칙만 공유할 수 있다.

향후 동일한 UI를 사용하는 독립 배포 프런트엔드가 두 개 이상 생기고 공용 컴포넌트 API가 안정되면, 그때 `src/design-system`만 별도 패키지로 추출할지 재검토한다. 현재는 별도 버전 관리, 패키지 배포, 호환성 검증 비용을 만들지 않는다.

## 2. 배경

Forest에는 이미 다음과 같은 좋은 기반이 있다.

- 전역 18px 본문과 1.7 줄간격
- 48px 조작 영역 유틸리티
- 키보드 포커스 표시와 reduced-motion 처리
- `ActionLink`, `SectionHeading`, `AsyncState`, `useFocusTrap` 같은 일부 재사용 요소
- 공개 홈과 조직도 중심의 접근성·반응형 Playwright 검사

그러나 이 기반은 전체 공개 화면과 관리자 CMS에 일관되게 적용되지 않았다. 페이지에서 원시 Tailwind 색상, 작은 글자, 서로 다른 반경·간격, 48px 미만 버튼을 직접 조합한다. 공용 `Button`, `IconButton`, `FormField`, `AccessibleDialog`, `StatusBadge`, `ResponsiveDataView`도 아직 없다.

가장 분명한 계약 불일치는 홈 배너다. 공개 홈은 `PublicHomeHero`를 렌더링하지만 관리자는 별도의 `HomeBannerHero`로 미리보기한다. 관리자는 자동 전환, 임의 글자색, 우측 카드 필드를 제공하지만 공개 컴포넌트는 이를 사용하지 않으며 자동 전환도 하지 않는다. 디자인 시스템 도입은 외형 정리뿐 아니라 이런 공개 화면과 관리자 미리보기의 동작 계약도 일치시켜야 한다.

## 3. 참고 자료 사용 원칙

- [Wall of Portfolios](https://www.wallofportfolios.in/wall-of-case-studies/)는 기존 UI 감사, 토큰 도입, 컴포넌트 확대, 기여·운영 규칙 같은 **구축 과정**을 참고한다.
- [getdesign.md](https://getdesign.md/)는 색상, 타이포그래피, 간격, 컴포넌트와 그 이유를 `DESIGN.md`로 표현하는 **명세 방식**을 참고한다.
- [DESIGN.md 형식](https://github.com/google-labs-code/design.md)은 기계가 읽는 토큰과 사람이 읽는 설계 의도를 함께 기록하는 방향만 참고한다. 현재 alpha 규격과 외부 CLI를 Forest 런타임의 필수 의존성으로 두지 않는다.

Starbucks, Wise, IBM/Carbon 등 특정 브랜드의 색상, 글꼴, 형태를 그대로 복제하지 않는다. 공개적으로 관찰한 패턴은 출발점일 뿐이며 Forest 브랜드, 전북 지역성, 50~60대 사용자의 읽기와 조작 요구를 최종 판단 기준으로 둔다.

## 4. 목표와 비목표

### 4.1 목표

1. 공개 화면과 관리자 CMS가 같은 의미 토큰과 기본 조작 컴포넌트를 사용한다.
2. 50~60대 사용자가 읽고 조작하기 쉬운 글자 크기, 대비, 터치 영역, 포커스 동작을 기본값으로 강제한다.
3. 새 페이지와 AI 기반 코드 작업이 동일한 시각 언어를 따르도록 저장소 루트에 Forest 전용 `DESIGN.md`를 둔다.
4. 공개 화면과 관리자 미리보기가 동일한 렌더러를 사용하도록 하여 편집 결과의 예측 가능성을 높인다.
5. 기존 화면을 한 번에 재작성하지 않고 배너와 조직도를 시작으로 프로그램, 게시글, 관리자 화면을 점진적으로 전환한다.
6. 토큰·컴포넌트·접근성·시각 회귀 검사를 완료 게이트에 포함한다.

### 4.2 비목표

- 여러 서비스를 위한 범용 디자인 시스템 저장소나 npm 패키지를 만들지 않는다.
- 다른 브랜드의 디자인을 통째로 설치하거나 복제하지 않는다.
- 백엔드 API나 콘텐츠 도메인 모델을 디자인 시스템 안으로 이동하지 않는다.
- 모든 기존 페이지를 한 번에 치환하지 않는다.
- 디자인 문서만 만들고 실제 토큰·컴포넌트·검증 없이 일관성이 확보됐다고 주장하지 않는다.
- 초기 단계에서 Storybook 같은 별도 도구 도입을 완료 조건으로 두지 않는다. 먼저 작은 개발·테스트용 컴포넌트 카탈로그와 Playwright 검사를 만든다.

### 5.1 `DESIGN.md`

`DESIGN.md`는 작업자와 AI 에이전트가 읽는 설계 계약이다. 다음 내용을 포함한다.

- Forest의 사용자와 브랜드 방향
- 시각 계층과 문장 톤
- 허용된 의미 토큰 이름과 사용 의도
- 타이포그래피, 간격, 표면, 컴포넌트 규칙
- 접근성 기본값
- 공개 화면과 관리자 화면의 차이
- 해야 할 것과 하지 말아야 할 것

정확한 런타임 색상·크기 값의 단일 기준은 `tokens.css`다. `DESIGN.md`는 값 자체를 별도의 정본처럼 중복 관리하지 않고 토큰 이름, 의도, 사용 예를 설명한다. DESIGN.md alpha 형식 지원은 참고 수준으로 유지하며, 외부 포맷이 바뀌어도 Forest 런타임이 영향을 받지 않게 한다.

### 5.2 `tokens`

`tokens.css`는 실제 화면이 사용하는 의미 토큰의 단일 원본이다. 전역 `index.css`가 이 파일을 먼저 import하고, Tailwind의 `forest-*` 별칭은 CSS 변수들을 참조한다. 현재 Tailwind 설정과 `index.css`에 각각 들어 있는 중복 색상 값은 전환 단계에서 제거한다.

초기 토큰 범위는 다음으로 제한한다.

- 색상: `brand-primary`, `brand-strong`, `brand-surface`
- 글자: `text-primary`, `text-muted`, `text-inverse`
- 표면: `surface-page`, `surface-card`, `surface-raised`
- 경계·포커스: `border-subtle`, `border-strong`, `focus-ring`
- 상태: `success`, `warning`, `danger`, `info`와 각 상태의 글자·표면
- 타이포그래피: 공개 본문, 관리자 본문, 레이블, 보조문구, 제목 단계
- 크기: `control-min-height`와 `icon-control-size`를 모두 48px 이상으로 보장
- 간격: 4px 기반의 제한된 간격 단계
- 형태: 컨트롤, 카드, 대화상자용 반경과 표준 패널 패딩

새 디자인 시스템 코드에서 원시 `green-*`, `blue-*`, `text-xs`, 임의 픽셀 높이 등을 직접 사용하지 않는다. 레거시 화면은 즉시 전부 금지하지 않고 전환 대상 목록으로 관리한다.

### 5.3 `primitives`

프리미티브는 도메인 데이터를 알지 않는 최소 조작 단위다.

- `Button`: primary, secondary, quiet, danger와 disabled, pending 상태
- `ActionLink`: 기존 구현을 `Button`과 같은 크기·variant 체계로 정렬
- `IconButton`: 48px 이상 크기, 필수 접근 가능한 이름, 위험 상태
- `FormField`: label, control, hint, error, required, `aria-invalid` 연결
- `AccessibleDialog`: 제목 연결, 초기 포커스, Tab 순환, Escape 종료, 원래 포커스 복귀, 스크롤 제어
- `StatusBadge`: 텍스트를 항상 제공하고 필요한 경우 아이콘을 함께 사용하며 색만으로 상태를 전달하지 않음
- `AsyncState`: 기존 로딩·빈 상태·오류·다시 시도 계약을 디자인 시스템에 맞춰 유지

프리미티브는 임의 색상과 임의 크기를 받지 않는다. 필요한 차이는 제한된 variant와 size로 표현한다.

### 5.4 `patterns`

패턴은 여러 프리미티브를 조합하지만 Forest 도메인 모델에는 의존하지 않는다.

- `Surface` 또는 `Panel`: 표면, 테두리, 패딩, 제목 영역
- `ResponsiveDataView`: 모바일 카드와 데스크톱 표를 같은 데이터로 렌더링
- `PageSubnav`: 프로그램·소식·ESG·자료실의 하위 탐색 통일

`HomeHero`, `OrganizationDirectory`, 프로그램 카드, 게시글 편집기처럼 서비스 의미가 포함된 컴포넌트는 `features`에 남긴다. 디자인 시스템은 이 컴포넌트들이 사용할 토큰과 프리미티브를 제공할 뿐, 모든 화면을 범용 컴포넌트로 만들지 않는다.

### 5.5 `catalog`

초기 카탈로그는 production route에 노출하지 않는 개발·테스트 전용 화면으로 만든다. 카탈로그 모듈은 development 또는 test 환경에서만 조건부로 import하고, production build에는 해당 route가 없음을 검사한다. 모든 primitive의 variant, hover/focus/disabled/pending/error 상태와 대표 패턴을 한곳에서 확인하며 Playwright 시각 회귀 대상으로 사용한다.

공용 요소가 충분히 안정되고 별도 협업 도구가 실제로 필요해질 때 Storybook 도입을 재평가한다.

## 6. 50~60대 사용자를 위한 시각·상호작용 원칙

- 공개 본문은 18px 이상, 줄간격은 1.6~1.7을 기본으로 한다.
- 관리자 핵심 정보, 입력값, 작업 버튼은 16px 미만으로 줄이지 않는다.
- 주요 조작 영역은 최소 48×48px로 한다.
- 일반 크기 텍스트와 버튼은 WCAG AA 수준의 대비를 만족하게 한다.
- 중요한 상태는 색뿐 아니라 텍스트와 필요한 경우 아이콘으로 표현한다.
- 키보드 포커스는 항상 눈에 띄며 border 색상 변화만으로 대체하지 않는다.
- 자동 슬라이드는 사용하지 않는다. 꼭 필요한 모션은 reduced-motion 환경에서 제거한다.
- 한 화면의 주 행동은 하나를 기본으로 하고 위험 행동은 분리한다.
- 순백색 일변도 대신 눈부심을 줄인 따뜻한 중립 표면을 사용할 수 있지만 글자 대비를 낮추지 않는다.
- pill 형태는 필터, 상태, 짧은 선택지처럼 의미가 있는 경우에만 사용한다.
- 12~14px 중요 정보, 초대형 96px 이상 제목, 과도한 여백, 다크 중심 화면, 장식적 애니메이션은 사용하지 않는다.
- 실제 Korean webfont를 번들하지 않았다면 특정 폰트가 적용된 것처럼 문서화하지 않는다. 라이선스와 파일을 확인하기 전까지 시스템 한글 sans fallback을 유지한다.

## 7. 공개 화면과 관리자 미리보기 계약

관리자 미리보기는 실제 공개 렌더러를 사용해야 한다. 같은 fixture와 편집 상태를 넘겼을 때 핵심 DOM 구조, 토큰, 반응형 동작이 동일해야 한다.

홈 배너의 기준 렌더러는 공개 화면에서 사용하는 `HomeHero` 하나로 통합한다. 현재 공개 화면에 없는 자동 전환, 임의 글자색, 우측 카드 필드는 관리자에서 제거하거나 명확한 미지원 항목으로 처리한다. 이후 해당 기능이 필요해지면 접근성, 공개 렌더러, 미리보기, 데이터 계약, E2E를 함께 변경한다.

이 원칙은 조직도, 프로그램 카드, 게시글 미리보기에도 순차 적용한다. 관리 화면이 공개 결과를 흉내 내는 별도 컴포넌트를 만들지 않는다.

## 8. 오류와 상태 처리

- `Button`은 처리 중 중복 제출을 막고 상태를 텍스트로 전달한다.
- `FormField`는 오류 메시지를 필드와 연결하고 저장 실패 시 입력을 보존한다.
- `AccessibleDialog`는 닫힌 뒤 실행한 조작으로 포커스를 돌려보낸다.
- `AsyncState`는 로딩, 빈 상태, 권한 부족, 서버 오류, 다시 시도를 구분한다.
- 디자인 토큰이나 필수 접근성 속성이 누락되면 테스트가 실패하며 원시 스타일로 조용히 대체하지 않는다.
- 디자인 시스템 컴포넌트는 API 오류 문구나 도메인 상태를 자체 생성하지 않는다. 화면이 사람이 이해할 수 있는 메시지를 전달하고 컴포넌트는 일관된 표시와 접근성 연결을 책임진다.

## 9. 단계적 전환 순서

### 1단계: 기준 고정

- Forest `DESIGN.md`와 의미 토큰 정리
- 현재 공개 홈·관리자·조직도의 대표 스크린샷과 접근성 동작을 회귀 기준으로 고정
- 새 코드의 의미 토큰 사용 규칙과 레거시 예외 목록 작성

### 2단계: 최소 프리미티브

- `Button`, `IconButton`, `FormField`, `AccessibleDialog`, `StatusBadge`
- 기존 `ActionLink`, `AsyncState`, `useFocusTrap`을 새 계약에 맞춰 재사용 또는 얇게 감싸기
- 개발·테스트 전용 카탈로그와 컴포넌트 검사 추가

### 3단계: 파일럿

- 공개 홈과 관리자 배너 미리보기를 단일 `HomeHero`로 통합
- 구조화 공개 디렉터리와 관리자 그룹 트리·폼, 미리보기·저장확인 대화상자를 대표 파일럿으로 전환
- 동일 fixture 기반 공개/미리보기 parity 검사 추가

### 4단계: 핵심 운영 화면

- 프로그램 관리와 편집 폼
- 게시글·공지 작성·수정
- 관리자 대화상자와 상태 메시지
- 모바일 카드·데스크톱 표를 `ResponsiveDataView`로 전환

### 5단계: 공개 레거시와 정리

- 프로그램, 소식, ESG, 자료실 하위 탐색 통일
- 남은 원시 색상, 작은 조작 영역, 접근 불가능한 클릭 행 제거
- 실제로 import되지 않는 stale CSS와 중복 설정을 사용 여부 확인 후 정리

각 단계는 독립적으로 빌드·테스트·검토할 수 있어야 하며, 전체 전환 완료를 기다리지 않고 승인된 단계만 다음 단계로 진행한다.

## 10. 검증 전략

### 10.1 컴포넌트 검사

- 모든 variant와 disabled, pending, error 상태 렌더링
- 키보드 포커스, Escape, 포커스 복귀
- accessible name과 오류 메시지 연결
- 48px 최소 조작 영역
- 의미 토큰 이외 원시 색상을 새 디자인 시스템 코드에서 사용하지 않는지 검사

### 10.2 E2E와 접근성

- Chromium 데스크톱, 768px 태블릿, 390px 모바일
- 200% 확대 reflow
- `prefers-reduced-motion`
- 대표 공개 화면과 관리자 화면의 axe 검사
- 예상하지 않은 console error, page error, request failure 감지
- 공개 HomeHero와 관리자 미리보기가 같은 fixture에서 동일한 핵심 내용·순서·상태를 표시하는지 검사
- 관리자 폼, 대화상자, 모바일 카드, 빈 상태, 오류 상태 검증

### 10.3 시각 회귀

- 개발 카탈로그의 primitive 상태
- 공개 홈과 관리자 배너 미리보기
- 공개·관리자 조직도
- 프로그램·게시글 관리자 대표 화면 (4단계 전환 시 추가)
- 운영체제별 파일명에 우연히 묶이지 않는 snapshot 정책과 명시적인 diff 기준 사용

자동 검사를 통과해도 모든 브라우저·보조기술의 무결점이나 특정 WCAG 등급의 완전 준수를 주장하지 않는다. 자동 검사 범위와 수동 확인 범위를 결과에 함께 기록한다.

## 11. 운영 규칙

- 새 화면은 먼저 기존 primitive와 pattern으로 표현할 수 있는지 확인한다.
- 새 variant는 실제 반복 사례가 두 곳 이상 있거나 명확한 접근성 요구가 있을 때 추가한다.
- 공개 결과를 편집하는 관리자 미리보기는 실제 공개 렌더러를 사용한다.
- 토큰 변경은 공개 화면, 관리자 화면, 카탈로그의 대표 screenshot과 접근성 검사를 함께 통과해야 한다.
- 위험하거나 기존 동작을 바꾸는 디자인 시스템 변경은 한 번에 전체 치환하지 않고 화면 단위로 전환한다.
- `DESIGN.md`, 토큰, 공용 컴포넌트 계약이 달라지는 변경은 같은 작업 단위에서 함께 갱신한다.

## 12. 별도 저장소 추출 재검토 조건

다음 조건이 모두 충족될 때만 독립 패키지나 저장소 분리를 검토한다.

1. 같은 토큰과 컴포넌트를 실제로 사용하는 독립 배포 프런트엔드가 두 개 이상이다.
2. 공용 primitive API가 여러 배포 동안 안정적으로 유지됐다.
3. 버전, changelog, 릴리스, 호환성 테스트를 맡을 운영 책임이 정해졌다.
4. 제품별 UI를 공용 시스템에 억지로 맞추지 않아도 된다.

조건을 만족하지 않으면 Forest 저장소 내부 관리가 기본이다.

## 13. 완료 기준

디자인 시스템 기반 도입은 다음을 모두 만족할 때 완료로 본다.

- Forest `DESIGN.md`와 의미 토큰의 역할이 명확하다.
- 핵심 primitive와 개발·테스트 전용 카탈로그가 존재한다.
- 공개 홈과 관리자 배너 미리보기가 같은 렌더러를 사용한다.
- 배너와 구조화 공개 디렉터리·관리자 그룹 편집/대화상자 대표 범위가 새 토큰·컴포넌트의 파일럿으로 전환됐다.
- 대표 공개·관리자 경로의 접근성·반응형·시각 회귀 검사가 통과한다.
- 미전환 레거시 화면과 알려진 제약이 문서화돼 있다.
- 사용자 검토 없이 원격 푸시나 운영 배포가 이루어지지 않았다.
